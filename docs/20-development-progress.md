## Decisions made during setup (beyond the architecture-planning decisions logged in `19-security-checklist.md`)

- **Pinned Next.js to 15.5.23 instead of the `latest` tag (16.3.0).** `create-next-app@latest` pulled Next 16.3.0, whose own generated agent-notes explicitly warn of breaking changes from typical training data and instruct reading bundled docs before writing code. For a security-critical, long-lived foundation, stability and familiarity outweighed being on the newest release. Next 15 is still fully modern App Router/Server Actions/Server Components.
- **`npm audit` overrides for `postcss`/`sharp`.** Next 15.5.23 bundles vulnerable transitive versions of both; added `overrides` in `package.json` pinning safe versions without needing to move off Next 15. Audit is clean (0 vulnerabilities).
- **ESLint flat-config compatibility shim.** `eslint-config-next@15.5.23` ships legacy (non-flat) shareable configs; `create-next-app`'s generated `eslint.config.mjs` assumed the newer flat-config-native format. Fixed using the standard `@eslint/eslintrc` `FlatCompat` shim.
- **Hand-wrote `components/ui/form.tsx`.** The `shadcn` CLI's registry in this version doesn't ship a `form` block; hand-wrote the standard, well-established shadcn form-wrapper pattern (Controller/FormProvider context plumbing) rather than fighting the CLI.
- **`Relationships: []` gotcha in hand-written Supabase types.** Supabase's generic type system (`GenericTable`/`GenericSchema` in `@supabase/postgrest-js`) requires every table entry to declare a `Relationships` array for `.rpc()` argument type-checking to work at all — omitting it doesn't error loudly, it silently degrades every `.rpc()` call to an untyped fallback. Documented here so it isn't rediscovered the hard way later, and so nobody "simplifies" the provisional types file by removing it.
- **Missing `tenants.country` column.** The original scope's tenants table (source doc S103) specifies `country`; migration 0001 omitted it. Caught while building the sign-up form (which collects country per spec S9.1). Fixed via `0002_add_tenant_country.sql` rather than editing 0001 — applied and verified live.
- **`handle_new_auth_user()` needed to also capture `phone`.** It only read `full_name` from `raw_user_meta_data`. A separate post-signup `profiles` UPDATE would have silently no-op'd under RLS when email confirmation is required (no session exists yet at that point), so the fix is in the trigger itself (`0003_profile_phone_from_signup.sql`), keeping profile creation fully transactional with the `auth.users` insert. Applied and verified live (a test signup's profile correctly showed the captured phone).
- **Embedded PostgREST relationship selects (`tenant:tenants(slug)`) don't type-check against the provisional hand-written types**, since `Relationships` arrays are empty (no FK metadata modeled). Worked around by querying the two tables separately (`lib/tenant/resolve-active-tenant.ts`) rather than fighting the types now. Revisit once real generated types (with relationship metadata) are in place — see the `types/database.types.ts` note above.
- **shadcn's `base-nova` style uses Base UI, not Radix — `asChild` doesn't exist.** Composition uses a `render` prop instead (`<Button render={<Link href="...">...</Link>} />`). Different convention from "classic" shadcn/ui docs and examples found online; worth remembering before reaching for `asChild` anywhere else in this codebase.
- **A literal `*/` inside a `/** ... */` doc comment silently truncates the comment early**, turning the rest into a parse error (hit this writing a comment that said `features/*/actions`). Avoid literal `*/` sequences inside block comments — use `<name>` placeholders instead of `*` wildcards in comment prose.
- **Next.js App Router treats any folder prefixed with `_` as private (excluded from routing).** A scratch verification API route placed at `app/api/_scratch-e2e-test/` 404'd for exactly this reason — moving it out of the underscore-prefixed folder fixed it. Relevant if a private/non-routed co-location folder is ever intentionally wanted under `app/`.
- **Supabase's `auth.signUp()` (not `admin.createUser()`) validates email format more strictly** — it rejected `@test.local` addresses outright ("invalid" error) but accepted `@example.com` (RFC 2606 reserved test domain). `admin.createUser()` doesn't apply the same check.
- **No browser automation tool is available in this environment.** Phase 1c's forms were verified by proving the exact service-layer code they call (`AuthService`, `TenantService`, `RoleService`) works correctly against the live database from a temporary, git-ignored test route hit with `curl` — not by clicking through the rendered UI in a real browser. Phase 1e's verification went one step further (real login through the actual `/api/auth/callback`-adjacent auth flow, then a real GET of `/t/[slug]` with the resulting session cookie, confirming the server-rendered HTML), which is stronger evidence but still not a literal click-through — no test has yet driven the client-side RHF form submission via simulated user interaction. This is an honest gap, not a claimed pass.
- **Merged `development` into `main`** (fast-forward, no conflicts) after discovering the user's Vercel project's Production deployment tracks `main`, which had been sitting on just the initial foundation commit while all of Phase 1c/1e/branding landed on `development`. Going forward, push both together promptly rather than letting them drift.
- **Generated `favicon.ico` from the custom SVG mark via `sharp`**, hand-assembling a modern PNG-in-ICO container (16/32/48px) rather than a raw bitmap ICO, since `sharp`/libvips has no native ICO encoder. Documented here so the regeneration approach doesn't need rediscovering if the mark changes: rasterize `app/icon.svg` at each size with `sharp`, then concatenate an `ICONDIR` header + `ICONDIRENTRY` per image + the raw PNG bytes.
- **`app/layout.tsx`'s font CSS variable name didn't match what `app/globals.css` expected.** `create-next-app`/shadcn scaffolding set `--font-geist-sans`, but the `@theme inline` block maps `--font-sans: var(--font-sans)` — so the Geist font was silently never applied; the app had been rendering in the browser's default sans stack the whole time. Fixed as part of switching to Outfit (now correctly named `--font-sans`) — worth knowing this was already broken before the font swap, not a regression caused by it.
- **Zod `.transform()` breaks React Hook Form's `useForm<T>()` typing.** A schema with `.transform()` has a different input type (what the form holds pre-submit, e.g. `""`) than its output type (what `z.infer` gives you, e.g. `string | null` after the transform) — but `useForm<T>` and `zodResolver` both need one consistent type. Fixed by keeping `validations/onboarding.ts`'s schema transform-free (plain `string` output) and doing the `"" -> null` conversion at the point of use in the server action instead. Worth remembering before reaching for `.transform()` in any other RHF-backed schema.
- **No new migration needed for the onboarding wizard's real steps** — `tenants` already had `business_type`/`website`/`anniversary_date`/`currency`/`timezone` from migration 0001, and `locations`/`location_hours` already existed too. Deliberately scoped Phase 1d's real forms to what the existing schema already supported, rather than expanding scope to match every spec field (e.g. logo upload, geofence coordinates) in this pass.
- **`resolveActiveTenant()`'s `needsOnboarding` flag is inferred from `locations` count being zero, not a dedicated `onboarding_completed_at` column.** Chosen deliberately to avoid a migration for a flag with only one real consumer right now; correct for Phase 1's one-location-per-tenant reality since the wizard's Step 2 is what creates the first location. Revisit if a tenant should ever be able to legitimately have zero locations while still being "onboarded" (unlikely before multi-location features land).
- **Zod string-refine instead of `.coerce`/`.transform()` for a numeric RHF field — same root cause as the earlier onboarding gotcha, new shape.** `validations/product.ts`'s `expectedPrice` needed numeric validation, but `z.coerce.number()` broke `useForm<CreateProductInput>()` + `zodResolver` (coerce's input type is `unknown`/`string`, its output type is `number` — RHF needs both identical). Fixed by keeping `expectedPrice` a validated `string` (`.refine()` checking it parses to a number `>= 0`), with the string→number conversion happening only at the point of use in `create-product.ts`'s server action (`Number(parsed.data.expectedPrice)`). Confirms the rule from 1d's decision log generalizes to `.coerce` as well as `.transform()` — any Zod method that changes the input/output type breaks RHF's `useForm<T>()`, not just `.transform()` specifically.
- **`sonner`'s `<Toaster />` was installed but never mounted anywhere.** The record-sale success toast (`features/sales/components/product-grid.tsx`) silently did nothing until this was caught by grepping for `Toaster` across `app/` and finding zero matches. Fixed by adding it to `app/layout.tsx`. Worth checking for on any future toast-library install — the import succeeding doesn't mean the portal is rendered.
- **Live-verified 1g and Phase 2 (2a–2d) via a single temporary scratch API route** (`app/api/scratch-verify/route.ts`, deleted immediately after the run, never committed — confirmed via `git status` showing a clean tree). It exercised the real `PlatformAdminService`/`TenantService`/`ProductService`/`BusinessDayService`/`SalesService` classes end-to-end: service-role for setup (creating two test auth users, granting one `platform_admins`, bootstrapping a test tenant via `TenantService.createTenant`), then an actual `signInWithPassword()` session (anon key + `Authorization: Bearer <access_token>` header) for every RLS-gated call after that, so the assertions prove real RLS policy behavior, not service-role-bypassed behavior.
